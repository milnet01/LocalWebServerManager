### What was learned

**The suite cannot see the compositor, and it stayed green through three
wrong mechanisms.** ADR-0007 specified a one-event-loop-tick delay after
`show`; measured against real KWin, that never works — the window opened at
1570,793 with a remembered position of 305,255. `Expose` plus one tick works
5/5. It also specified that only the position need be sent, since `resize()`
is honoured under Wayland; in fact KWin's geometry write is authoritative, so
a script that does not carry the size pins the window at its undecorated
minimum. And converting the client size to a frame size in the app sends a
zero decoration, because the window is not decorated yet when placement runs
— `c.clientGeometry`, inside the script, is where that answer lives. Every
Wayland test passed against all three, because they substitute a stand-in for
KWin that honours whatever it is handed whenever it is handed it. **For
anything the compositor owns, running the app is the only evidence.** A KWin
script's `print()` reaches `journalctl --user -u plasma-kwin_wayland`, which
is how all of it was read.

**Setting a position and reading one are not the same capability.** ADR-0007
treated "Wayland discards the position" as a restore problem that KWin
closes. It is also a capture problem that nothing closes: a client is never
told where it is, so Qt answers 0,0 — a plausible value, not an error, which
is why it would have been saved as though true. Put to the user, who chose
the honest limit over adding a D-Bus service.

**Six of the twenty findings are in code written the same day**, and the two
most severe both sit where a docstring asserted the opposite: `settings.py`
claimed three times that a refusal there cannot lose data, and
`supervisor.py`'s trust model claimed an escaping symlink is refused
outright. In both cases the sibling module states the correct rule in almost
the same words — `registry.py` for the first, ADR-0003 for the second. **A
claim in prose beside the code is not a check on the code**, and this batch
is the clearest measurement of that the project has taken.

**A mutation harness must restore from its own copy, never from git.** Using
`git checkout` to revert a hand-applied mutant reverted uncommitted work and
destroyed about an hour of edits, recovered only because they were still in
the session's context. Recorded in `CLAUDE.md`.

### A correction to this close's own claim

The FP08 section intro in `ROADMAP.md`, and the fold-in commit message, both
say every finding was verified against the code before filing. **That
overstates it.** Three were reproduced outright (LWSM-1162, LWSM-1163,
LWSM-1164), eleven more were checked directly with greps and probes, and
**six rest on the review lane's quotation alone** — LWSM-1167, LWSM-1168,
LWSM-1169, LWSM-1175, LWSM-1178, LWSM-1179, plus three of LWSM-1180's five
docstrings.

Those six now carry a `Verification status` note on the bullet itself,
which is where a worker will read it. The intro could not be corrected in
place: this project's roadmap is served from the store and re-rendered on
every write, so a hand edit to a section intro is reverted, and no verb
amends one. The commit message could not be corrected either — that needs a
force-push `commits.md § 4.2` withholds.

Recorded here because the failure is worth more than the correction: a
close that dispatches lanes and files what they return is doing triage, not
verification, and calling it verification is how a lane's plausible
reasoning becomes a fix for a defect nobody confirmed. **Read the bullet's
verification note before implementing it.**
